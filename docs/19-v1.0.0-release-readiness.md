## 3. 数据与升级保护

### 3.1 精确升级

- [ ] 使用真实不可变 `ghcr.io/xwordsman/nextbuf:0.13.10` 建立包含管理员、普通用户、节点、主题、首帖、回复、修订、提及、附件、互动、通知、举报、角色、制裁和信任状态的基线。
- [ ] 由正式候选镜像执行 `nextbufctl` 备份和 `0.13.10 -> 1.0.0` 升级，而不是从当前源码伪造旧版本。
- [ ] 生产只提供维护窗口备份与只读基线；升级、恢复、删卷、故障注入、邮件 replay 和账号最终注销均在该备份恢复出的隔离副本执行，不直接改写线上数据库。
- [ ] `nextbufctl upgrade 1.0.0 --verify-objects` 在停写窗口自动生成 before/after HMAC 快照、比较报告和 SHA-256；稳定表/分组指纹一致，目标迁移与 Schema 后置检查通过，原始/派生附件校验通过。
- [ ] 升级前后的 User UUID/UID、永久用户名别名、Topic number、Post position、修订链和公开附件引用由脱敏全局指纹及人工抽样共同证明一致，证据文件不包含这些原始值。
- [ ] Better Auth 账号、密码凭证、邮箱验证状态和有效 Session 按发布说明保持；升级不要求用户重新注册。
- [ ] PostgreSQL 中已提交事实不依赖 Redis；清空 Redis 后队列、周期任务和派生计数可恢复。
- [ ] Handler 副作用、既有失败解决、`ProcessedJob` 与 Outbox `processed_at` 在同一 PostgreSQL 事务提交；提交前处理租约再次栅栏。
- [ ] SMTP I/O 位于事务外；每次发送有持久 attempt token/generation。明确未接受的临时错误自动重试，永久拒绝终结，可能已接受的错误持久化为 `outcome_unknown`，普通重试不得再次发送。
- [ ] `outcome_unknown` 重放要求管理员显式确认重复投递风险并进入治理审计；请求和执行都拒绝有效 PostgreSQL 处理租约，失租旧 attempt 的成功、失败和迟到完成不得改写新状态。
- [ ] 已发布未处理事件在 Redis 丢失后自动恢复，已完成历史不再进入恢复扫描；replay 已执行的旧失败不阻断恢复，新最终失败重新等待人工 replay。
- [ ] 未知迁移、缺失迁移、镜像/配置版本不匹配时 Web/Worker 快速失败且不进入假健康。
- [ ] 升级耗时、停写窗口、数据库大小和验证查询记录到证据中。

## 4. 身份、注销与管理员连续性

- [ ] Better Auth 继续拥有密码、Session、验证、OAuth 和 Cookie 行为；没有平行认证实现。
- [ ] Better Auth 通用 `/update-user` 不能绕过 NextBuf 的昵称、头像、Profile、用户名冷却和永久别名管线；认证集成测试确认拒绝后 User/Profile/Alias 与头像对象均不变。
- [ ] 账号注销申请可在 14 天内撤销，到期执行器具备持久重试、小批量锁和失败隔离。
- [ ] 注销后账号不可登录；邮箱、凭证、Session、私人资料/草稿/附件和私有互动按 [ADR-0021](./adr/0021-final-account-deletion-and-data-retention.md) 清理。
- [ ] 注销按 ADR-0021 保留不可变 UID、公开主题/回复、楼层、公开修订/附件引用、永久用户名占用及必要治理证据。
- [ ] 注销任务重复执行幂等，单个对象存储故障不会永久阻塞其他到期请求。
- [ ] 大账号注销使用集合式 SQL，不把附件、私人内容或邮件 UUID 无界载入 Node.js；集成夹具至少覆盖 256 组事实。轮换 `AUTH_SECRET` 后，当前与全部历史用户浏览哈希被删除，匿名及其他用户哈希不受影响；历史密钥恢复与安全移除条件按 ADR-0011/0021 验证。
- [ ] SMTP 原始错误、收件人和用户名不进入 BullMQ、Worker 日志或 PostgreSQL；注销和邮件完成/失败/replay 统一遵循 `EmailDelivery -> WorkerJobFailure -> OutboxEvent` 锁序，`sending` 与 `outcome_unknown` 阻止最终注销，迟到回调不重新写回已删除投递。
- [ ] 管理员在交接并撤销 `admin/site` 前不能申请最终注销。
- [ ] 撤销角色、暂停/封禁、注销申请和凭证解绑在同一连续性锁/规则下，不能产生 0 位可登录站点管理员。
- [ ] 连续性管理员要求 active、邮箱已验证、无注销计划、无有效 suspend/ban 且有 credential 密码；TL 不产生管理资格。
- [ ] doctor 与后台对 0 位管理员报失败、1 位报冗余不足警告、2 位及以上通过；首次安装邮箱验证后也执行同一检查。
- [ ] 首次安装 claim 使用 PostgreSQL 时钟租约和随机 `claimId`；旧请求失去所有权后不能授予首管、写完成状态或删除后继 claim。最终事务必须锁定 credential，并用 Better Auth verifier 证明当前表单密码；该过程不创建 Session/Cookie，密码不匹配时不得授予角色、写完成状态或覆盖哈希。

## 10. 发布顺序

1. 冻结功能和迁移，完成上面所有候选门槛。
2. 在独立变更中把版本提升为 `1.0.0`，同步 Dockerfile、示例和文档；主线完整 CI 通过。
3. 复核已启用的 GitHub Repository Ruleset `20172767` 仍保护 `refs/tags/v*` 的创建、更新和删除，并且仅保留发布负责人 bypass。
4. 从该 commit 创建带签名说明的不可变 `v1.0.0` 标签；禁止移动标签。
5. 标签流水线构建并验证精确 SemVer 镜像、归档、校验和、SBOM/provenance。
6. GitHub Release 和全部资产成功后，当前标签在共享锁外写入并远端验证完成回执。
7. 后续共享锁任务重新选择全局最高完整稳定 Release，复核回执、资产、SemVer 镜像和现有通道后，才把回执绑定的 manifest 调和为 `latest`。
8. 核对公开 Digest、归档 SHA-256、Release 状态和 `latest == 1.0.0`，填写本文件第 1 节。
9. 在真实部署执行发布后冒烟并观察 Web、Worker、数据库、队列、邮件和存储；严重异常按备份恢复边界处理并发布更高补丁，不移动已有 SemVer。

## 11. 发布阻断级别

- **P0**：已确认利用、数据不可恢复损坏、错误公开私人数据、发布产物身份冲突。必须阻断。
- **P1**：默认安装/升级失败、核心认证或发帖链路不可用、管理员连续性失效、备份无法恢复。必须阻断。
- **P2**：有可行规避且不损害数据/安全的局部回归。必须在发布说明列出负责人和补丁计划，由发布负责人明确接受。
- **P3**：文案、低影响视觉或后续增强。可进入后续版本，但不得借机扩大 `v1.0.0` 范围。
