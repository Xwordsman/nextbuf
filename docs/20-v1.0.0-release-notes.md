# NextBuf `v1.0.0` 发布说明（草案）

> `v1.0.0` 尚未发布。本文用于稳定化和验收，Digest、校验和、CI 证据与已知问题未补齐前不能作为生产升级指引。当前完整发布版本仍是 `v0.13.10`。

## 1. 版本定位

`v1.0.0` 是 NextBuf 首个稳定社区版本。它冻结 V1 的核心数据、配置和单机部署合同，重点关闭公开 Beta 后的账号生命周期、管理员连续性、升级恢复和支持政策，不加入金币/能量、插件、交易、支付或开放 API。

本版本包含：

- 统一 Next.js Web/管理后台/API 与独立 Worker；
- PostgreSQL 18 事实数据、Redis/BullMQ 可恢复队列；
- Better Auth 邮箱密码、验证、重置、Session 和可选 GitHub OAuth；
- 节点、稳定数字主题、回复楼层、Markdown、附件、互动、搜索和通知；
- 举报、制裁、角色、信任等级、审计和 Session 绑定管理员二次验证；
- amd64/arm64 单镜像、四容器 Compose、宝塔单文件入口和 Linux x64 standalone；
- setup/preflight、doctor、备份、恢复和保守升级工具。

GitHub Release 正文由标签流水线从本文件生成，并插入该标签的 commit、Digest、归档校验和与 CI 证据。

## 2. 相对 `v0.13.10` 的稳定化变更

以下稳定化变更已进入 `v1.0.0`，并由同一标签流水线验证：

- [x] 已实现到期账号注销：保留公开内容、UID、楼层和必要治理证据，清理凭证、Session、私人数据及旧 actor 通知邮件，区分历史治理证据与当前案件指派，并通过数据库墓碑守卫关闭并发重建边界；注销与邮件最终失败统一使用 `EmailDelivery -> WorkerJobFailure -> OutboxEvent` 锁序。
- [x] 已统一管理员连续性规则，覆盖角色撤销、暂停/封禁、注销和 credential 解绑，并增加 doctor/后台诊断。
- [x] 首次安装 claim 使用 PostgreSQL 时钟租约、随机所有权 ID 和最终事务栅栏，迟到请求不能写入首管事实或删除后继 claim；最终事务锁定 credential，并用 Better Auth verifier 证明当前表单密码，不创建 Session/Cookie，密码不一致时不授予角色、不写安装完成状态且不覆盖密码哈希。
- [x] Outbox 增加持久 `processed_at`、只扫描已发布未完成事件的部分索引和可续租处理栅栏；Handler 副作用、失败解决、`ProcessedJob` 与 `processed_at` 原子提交，Redis 丢失及 replay 后再次丢失均可恢复，新最终失败重新等待人工重放。
- [x] 邮件发送移出数据库事务并加入持久 attempt token/generation；只有明确未接受的临时故障自动重试，永久拒绝进入失败，可能已接受的结果独立标记为 `outcome_unknown`。管理员重放该状态前必须确认重复投递风险，PostgreSQL 处理租约和 attempt fence 阻止新旧 Worker 并行覆盖。
- [x] 发布通道改为 `main -> edge + sha-*`；稳定标签的 Release 资产和完成回执验证后才更新 `latest`。
- [x] 主线为每个架构冻结带 SBOM/provenance 的 `sha-<commit>-<架构>` 源索引，在冒烟前固定运行时 Digest，并把运行时与源 index Digest 作为 Actions artifact 交给后续任务；完整 `sha-<commit>` 通过 OCI 身份验证后供人工验收。演练和标签流水线复用同一来源，不重新构建；SemVer index 与已验收 `sha-<commit>` Digest 完全相同，并保留两个架构的 attestation 描述符及其 OCI 运行时引用关系。
- [x] Release 完成回执在首次上传后、复用和稳定通道提升前重新核对标签 commit、版本、OCI index/amd64/arm64 Digest、三项资产 SHA-256 与归档旁路校验和；失败回执会被移除。Registry 不明确失败不会创建标签，稳定提升只使用回执绑定的 `image@sha256:...`。每个标签在共享锁外独立完成并验证回执，只有后续调和使用跨标签串行锁；每个存活调和任务重新选择全局最高完整稳定 Release，当前 `latest` 的镜像版本和平台成员还会阻止通道倒退。
- [x] 建立稳定版本支持周期、私密安全报告和正式版发布/人工验收文档。
- [x] 最终配置合同和 [`v1.0.0` Provider 支持矩阵](./22-v1.0.0-provider-support-matrix.md)已经冻结；数据库迁移清单已经冻结。真实部署选择的 SMTP、存储和可选 OAuth 仍须写入人工验收记录。
- [x] 宝塔固定四容器实例可以通过 `nextbufctl backup --baota` 在停写窗口导出兼容 `nextbuf-backup-v1` 的 PostgreSQL、完整配置、源编排和运行镜像/卷身份；local 模式同时归档附件，S3 模式记录对象清单并要求同窗口 Provider 快照/版本/复制。合法复杂轮换密钥按 Compose 语义无损保留，中断清理会等待 daemon 侧 stop 并有界重试恢复服务，helper 通过临时容器文件复制运行；`restore --keep-stopped` 允许隔离副本先替换域名、SMTP、OAuth、代理和存储 Provider，再显式启动 Web/Worker。
- [x] 生产与独立 runtime lockfile 将 `fast-uri` 统一覆盖到 `3.1.5`，关闭 `GHSA-7p8r-x3mc-p8w7`；两套 high/critical 生产依赖审计均无已知漏洞。

自动化清单为 124 项单元测试、91 项真实 PostgreSQL/Redis/Mailpit 集成和 14 项 Playwright；标签流水线在同一提交上运行这些门槛，Release 正文中的产物身份以该标签回执为准。

发布时删除复选框和规划措辞，只保留已经进入标签的变更，并列出精确迁移名称。

## 3. 支持的升级路径

支持的直接来源是精确 `v0.13.10`。更早版本必须按各自发布说明先升级到 `v0.13.10`；不完整的 `v0.13.9` 不作为升级基线。

升级前必须：

1. 记录当前精确版本、镜像 Digest、迁移状态和 Web/Worker 健康。
2. 运行 `nextbuf doctor`，处理数据库、Redis、Worker、队列、邮件和存储错误。
3. 停止非必要配置变更并创建通过校验的 PostgreSQL、附件和配置备份。
4. 验证备份可以在隔离空环境恢复；S3 部署还需验证对象版本/备份。
5. 阅读本文件的迁移耗时、停机窗口、已知问题和回退限制。

受控升级入口：

```bash
./nextbufctl upgrade 1.0.0
```

宝塔入口先从面板导出当前实际编排，并使用本 Release 的工具执行：

```bash
NEXTBUF_BACKUP_DIR=/restricted/backups \
  ./nextbufctl backup --baota /root/nextbuf-live-compose.yml
```

内部 `SHA256SUMS`、外层 `.tar.gz.sha256`、数据库 dump 清单以及所选存储的校验全部通过后，才显式拉取 `ghcr.io/xwordsman/nextbuf:latest` 并重建 Web/Worker：local 核对附件归档，S3 核对对象清单与同窗口 Provider 快照/版本/复制身份。发布验收必须证明此时 `latest` 与不可变 `1.0.0` manifest Digest 相同。需要完全可复现时把镜像固定为 `1.0.0`，不要只记录浮动标签。把生产归档恢复为隔离副本时增加 `--keep-stopped`，在写进程启动前切断生产 Provider；完整步骤见[运行手册](./13-installation-operations-runbook.md#44-宝塔生产导出到受控-compose)。

## 4. 数据与兼容性

稳定化不得重写既有 User UUID/UID、永久用户名别名、Topic number、Post position、修订链、公开内容或附件引用。账号注销只按 [ADR-0021](./adr/0021-final-account-deletion-and-data-retention.md) 的保留/清理合同处理到期申请，不把社区公开讨论从楼层中物理抽走。

本版本的数据与配置变化：

- 新增迁移：`20260730120000_account_deletion_finalization`、`20260731120000_outbox_processed_status` 与 `20260731180000_email_delivery_attempt_fencing`；三者使用显式 PostgreSQL 事务，迁移入口在 Prisma 写入记录前检查已知身份/注销数据冲突，并为已确认事务回滚的失败提供受限 `--resolve-rolled-back` 恢复命令。`prisma/migration-baselines/v1.0.0.json` 已将它们连同此前 13 条公开迁移冻结为 16 条发布迁移及 SHA-256。升级入口始终要求成功记录是该清单的 checksum 精确连续前缀；存在 `runtime.initialized` 的实例必须至少完整匹配 `v0.13.10`，失败记录还必须匹配发布 checksum、前缀位置与当前 schema marker。Outbox 迁移从既有 `ProcessedJob.completed_at` 回填 `processed_at` 并建立部分恢复索引；邮件迁移加入 attempt token/generation、`outcome_unknown` 和重放风险确认时间，并把升级时遗留的 `sending` 保守转换为结果未知。
- 迁移耗时与锁范围：三条迁移都在显式事务中执行，包含 `ALTER TABLE`、约束/触发器/索引创建和既有行回填，可能在相关表上等待或持有排他锁；耗时随用户、Outbox、邮件及治理数据量变化，不承诺固定分钟数。升级必须保持 Web/Worker 停写，并先在生产备份恢复出的隔离副本逐阶段测量迁移与 readiness 时间；实测值写入受限验收记录，用它确定正式维护窗口。
- 配置新增：`SMTP_CONNECTION_TIMEOUT_MS=15000`、`SMTP_GREETING_TIMEOUT_MS=15000`、`SMTP_SOCKET_TIMEOUT_MS=60000`；本版本没有弃用变量。
- Provider 变化：SMTP 错误采用 retryable/permanent/outcome-unknown 三类合同；S3 与 GitHub OAuth 支持边界不变，正式支持范围见 [`v1.0.0` Provider 支持矩阵](./22-v1.0.0-provider-support-matrix.md)。具体厂商只有完成实例级人工验收后才进入发布记录。

Redis 不是备份事实来源，可以重建；PostgreSQL 必须与所选存储事实成套保护：local 备份附件归档，S3 备份对象清单及 Provider 快照/版本/复制。Web 与 Worker 必须始终运行同一版本和配置。

## 5. 回退边界

迁移前失败可以继续使用原镜像和未变更数据。目标 setup 开始迁移后，失败路径保持 Web/Worker 停止，先检查日志和发布说明。

迁移成功后不要直接让 `v0.13.10` 读取 `v1.0.0` Schema。只有最终发布说明明确声明代码回退兼容时才允许切回旧代码；否则恢复升级前 PostgreSQL、附件、配置和旧镜像。`latest` 或 SemVer 标签都不会因故障被重写，修复通过更高补丁版本发布。

## 6. 已知限制

以下边界不是 `v1.0.0` 阻断项，但必须保持明确：

- 在线成员追踪未实现，页面保持真实空状态。
- V1 只支持单社区、单机四服务默认拓扑，不宣称多租户或多实例高可用。
- PostgreSQL 18 是唯一官方数据库；Redis 8 是队列/缓存依赖，不支持 MySQL 替代。
- Mailpit 仅用于开发、测试和 CI，生产必须配置真实 SMTP。
- S3 对象的跨区域/版本备份由部署者配置；数据库备份不包含对象正文。
- 不执行第三方服务端插件，不提供稳定公共 API、支付或交易能力。
- 官方支持边界以 [SUPPORT.md](../SUPPORT.md) 为准，第三方面板和 Provider 自身故障由对应厂商处理。

发布后发现的 P2 问题必须在后续补丁说明中追加影响、规避方式、负责人和目标版本；P0/P1 不进入稳定 Release。
