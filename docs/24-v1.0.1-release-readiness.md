# `v1.0.1` 发布就绪与验收清单

> 本文件是 `v1.0.1` 的候选冻结和 GO/NO-GO 合同，不表示尚未生成的 CI、tag、OCI、Release 或生产证据已经完成。公开证据绑定不可变 commit；真实配置、备份、邮箱、用户和服务器输出只保存在受限目录，不提交仓库。

## 1. 版本边界

`v1.0.1` 是 `v1.0.0` 的向后兼容补丁，Must 范围只有：

- 隐藏节点主题不能从数字 URL、metadata、列表、搜索或互动接口向匿名/普通用户泄漏；有效作者和治理角色保留只读处置能力。
- `AUTH_TRUSTED_ORIGINS` 由同一解析合同同时提供给 Better Auth 和 NextBuf 写接口，只接受精确 HTTP(S) Origin；生产公网 Origin 必须为 HTTPS。
- Worker 在依赖、BullMQ、心跳或调度初始化失败时释放已经取得的 Worker、Redis、Prisma、系统队列、定时器和心跳资源；原始启动错误必须保留。
- 邀请注册只有在明确确认 Better Auth 用户没有持久化时才能退回预约次数；post-commit hook、后续审计或提交状态检查失败都不得让单次邀请码重用。
- 发布链路使用已发布 `v1.0.0` 作为直接升级基线，Release body 从当前包版本解析；`1.0.0 -> 1.0.1` 使用独立无迁移升级冒烟。

本补丁不得增加产品功能、数据库迁移、破坏性配置迁移、公开数据模型、容器、在线成员伪数据，或修改 Better Auth 的密码、Session、验证、OAuth 与 Cookie 所有权。`v1.1.0`、金币/能量、插件、交易、支付和开放 API 均不在范围内。

## 2. 冻结身份与本地门槛

- [ ] `package.json`、runtime package、Docker build arg、项目常量、示例环境和 release notes 全部为 `1.0.1`。
- [ ] `prisma/migration-baselines/v1.0.1.json` 与 `v1.0.0.json` 都是相同顺序和 SHA-256 的 16 条迁移；历史 SQL 未修改。
- [ ] `pnpm check` 通过文档链接、Prettier、ESLint、严格 TypeScript 和全部单元测试。
- [ ] `pnpm migration:verify`、`pnpm build`、Release body smoke 和 `git diff --check` 通过。
- [ ] 根项目与 standalone runtime 的生产依赖审计没有已知漏洞。
- [ ] DCO sign-off 存在，工作区干净，`origin/main` 与本地冻结 commit 相同。

冻结 commit、DCO、测试时间和本地日志记录在受限发布记录；源码文档不通过发布后的补写提交改变候选身份。

## 3. 五项补丁的可执行判据

### 3.1 隐藏节点

- [ ] 匿名和无角色用户访问已知数字主题地址得到不存在状态，`generateMetadata` 不返回标题。
- [ ] 有效主题作者、节点版主、全局版主和管理员可以读取治理所需主题；被暂停或删除身份不能借角色读取。
- [ ] 隐藏节点主题不能新增回复/回复草稿、点赞、收藏、关注、阅读桶或浏览桶；公开列表、节点页、搜索、热门和个人互动列表均不返回它。
- [ ] 附件下载继续按作者/治理权限检查，不能因主题页只读放宽对象访问。

### 3.2 可信 Origin

- [ ] `APP_URL` Origin 与 `AUTH_TRUSTED_ORIGINS` 被规范化、去重，并同时传入 Better Auth 与 `hasSameOrigin`。
- [ ] 默认端口和大小写规范化后精确匹配；未配置 Origin、序列化不精确值和无 Origin 写请求被拒绝。
- [ ] 非 HTTP(S)、凭据、非根路径、查询（含空 `?`）、片段（含空 `#`）和通配符被拒绝。
- [ ] 生产公网 HTTP 被拒绝；明确 loopback HTTP 仍可用于本地诊断。

### 3.3 Worker 启动失败

- [ ] 数据库/Redis 健康失败、邮件队列隐私迁移失败、BullMQ ready 失败、心跳 upsert 失败和 scheduler 初始化失败均退出启动。
- [ ] 已取得的 BullMQ Worker 使用强制 close；专用连接、系统队列、全局 Redis/Prisma、定时器和已写心跳被清理或标记停止。
- [ ] BullMQ 构造器同步失败时，由创建函数关闭已经创建但尚未移交所有权的 Redis 连接。
- [ ] 清理失败不能覆盖原始启动错误；正常 SIGINT/SIGTERM 的既有优雅停机合同不回归。

### 3.4 邀请注册

- [ ] Better Auth 完全回滚且查询明确不存在用户时，预约次数被安全退回。
- [ ] `identity.user.registered` post-commit hook 失败时用户和 credential 存在，预约次数保持消费。
- [ ] 外层 `identity.invite.consumed` 审计失败时预约次数保持消费。
- [ ] 提交状态查询或退回补偿自身失败时公开响应保持非枚举，错误进入脱敏日志，邀请码不会因不确定状态重用。

### 3.5 发布链路

- [ ] 工作流只出现一次 `NEXTBUF_UPGRADE_BASELINE: 1.0.0`，并在 amd64 主线/演练/tag 调用 `docker-patch-upgrade-smoke.sh`。
- [ ] 补丁升级从真实 GHCR `1.0.0` 启动，升级前后均为 16 条相同迁移，持久身份、主题、首帖、修订和附件引用/对象不变。
- [ ] 历史 `docker-upgrade-smoke.sh` 继续以 `0.13.10` 为默认基线，保留三条 `v1.0.0` 迁移的失败/恢复覆盖，但不冒充本补丁直接升级门槛。
- [ ] 错误 tag/内嵌版本组合在备份和迁移前拒绝；成功路径执行 `nextbufctl upgrade 1.0.1 --verify-objects`，comparison 为 `pass`。

## 4. 同一 commit 的自动化发布门槛

- [ ] `main` CI：真实 PostgreSQL/Redis/Mailpit 集成、构建、Playwright、Linux x64 归档、amd64/arm64 镜像冒烟、amd64 `1.0.0 -> 1.0.1` 升级全部通过。
- [ ] `release_rehearsal=true`：同一 commit 重跑深度恢复、故障注入、升级与双架构身份验证；只写 staging/`sha-*`/`edge`，不写 SemVer 或 `latest`。
- [ ] 分支保护/Ruleset 对冻结 commit 已满足；P0/P1 为零，其他风险有负责人、影响和回退说明。
- [ ] 演练 OCI index、amd64/arm64 runtime Digest、commit、归档和 SBOM artifact 身份写入受限发布记录。

## 5. 正式 tag 与稳定通道

- [ ] 在通过演练的同一 commit 创建带注释且不可变的 `v1.0.1` tag；不重新构建替代候选。
- [ ] tag CI 重新通过，GitHub Release 非 draft/非 prerelease，Linux x64 归档、SHA-256、Source SBOM 和完成回执齐全。
- [ ] `1.0.1` OCI index 与演练候选相同，amd64/arm64 成员及 attestations 完整；Release body 中 tag、commit 和 Digest 一致。
- [ ] 完成回执远端复核后，`latest` 才提升为相同 OCI index；若已有更高稳定版，调和器不得回退。

## 6. 管理员连续性与发布豁免

升级工具的最低硬门槛始终是至少一位可接管管理员：`admin/site`、active、邮箱已验证、无注销申请/计划、无有效 suspend/ban，且有非空 credential 密码。0 位必须 NO-GO。

ADR-0022 的正式 Release 默认门槛是 2 位。项目所有者在 2026-08-06 对 `v1.0.0` 明确接受了单管理员风险；该历史豁免不能自动证明 `v1.0.1` 已获批准。`v1.0.1` tag 前必须满足其一：

- [ ] 已配置并验证第二位合格管理员；或
- [ ] 项目所有者对 `v1.0.1` 明确重新批准单管理员发布，受限发布记录保留原话、日期和风险，`administrator_redundancy_missing` 仍显示为警告。

## 7. 生产升级

- [ ] 在维护窗口对实际宝塔编排执行并校验全新一致性备份；local 附件核对 SHA-256，S3 另有同一窗口 Provider 快照/版本。
- [ ] 记录升级前 `/api/version`、四容器健康、Doctor、16 条迁移、镜像身份和脱敏数据连续性摘要。
- [ ] 拉取正式 `1.0.1`/`latest` 相同 OCI index，Web 与 Worker 使用同一版本；不删除卷，不执行 `down -v` 或 prune。
- [ ] 执行 `1.0.0 -> 1.0.1`，确认无新 DDL，acceptance comparison/对象校验通过后才启动 Web/Worker。
- [ ] 升级后验证四容器、Doctor、16 条迁移、管理员登录、普通用户登录、主题/回复/附件、通知邮件和 Worker；持续观察错误、队列、Outbox、邮件与心跳。

若 setup 已开始后出现迁移身份、比较、附件、管理员、登录或健康失败，保持 Web/Worker 停止并恢复 PostgreSQL、附件/Provider、配置和匹配镜像的整套备份；不得只把镜像标签改回 `1.0.0`。

## 8. GO/NO-GO

只有第 2-7 节所有适用 Must 完成、P0/P1 为零、单管理员条件得到满足或本版本明确豁免，才可记录 `GO`。任何以下情况必须 `NO-GO`：

- 冻结 commit、演练、tag、Release、OCI 或运行镜像身份不一致；
- `1.0.0 -> 1.0.1` 没有真实 pull、16 条迁移发生变化或 acceptance comparison 失败；
- 五项补丁缺少正常/拒绝/故障路径回归；
- 合格管理员为 0，或只有 1 位且没有本版本明确发布豁免；
- 正式产物/完成回执不完整，或生产备份未验证。
