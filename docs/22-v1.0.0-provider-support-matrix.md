# `v1.0.0` Provider 与运行环境支持矩阵

本文冻结 NextBuf `v1.0.0` 的官方运行环境和外部 Provider 合同。它说明应用承诺兼容的协议、版本和配置边界，不代表 NextBuf 为第三方厂商的账号、网络、配额、计费、数据保留或服务可用性背书。

正式发布证据必须区分两件事：仓库中的配置合同和自动化门槛已经通过；部署者选择的真实域名、SMTP、对象存储和 OAuth 账号仍须按[人工验收模板](./21-v1.0.0-manual-acceptance.md)记录实例级结果。

## 1. 支持级别

| 级别 | 含义 |
| --- | --- |
| Required | V1 运行所必需，官方安装、升级和恢复门槛覆盖 |
| Supported | 官方实现并维护公开配置合同 |
| Optional | 未配置时功能隐藏或使用受支持的内置路径 |
| Development only | 只用于开发、测试和 CI，不用于公开生产站点 |
| Out of scope | V1 没有实现或没有兼容承诺 |

## 2. 数据库、缓存与搜索

| 组件 | 级别 | `v1.0.0` 合同 | 不在合同内 |
| --- | --- | --- | --- |
| PostgreSQL 18 | Required | 唯一官方事实数据库；支持官方 Compose 的 `postgres:18-alpine` 和满足相同 PostgreSQL 18 语义的托管实例；TLS 通过 `DATABASE_URL`/`DATABASE_DIRECT_URL` 参数配置 | MySQL、MariaDB、SQLite、CockroachDB 兼容模式和更早 PostgreSQL 主版本 |
| Redis 8 | Required | BullMQ、缓存和限流依赖；官方 Compose 使用 `redis:8-alpine`；服务必须支持 BullMQ 所需命令并采用 `noeviction` 容量策略 | 只实现部分 Redis 命令的缓存产品，以及把 Redis 当成唯一业务事实来源 |
| PostgreSQL Search | Supported | V1 固定使用 `PostgresSearchProvider`、PostgreSQL FTS 与 `pg_trgm`；没有额外搜索容器 | Meilisearch、OpenSearch、Elasticsearch 和 `SEARCH_*` 配置切换 |

Web 与 Worker 必须运行相同的 NextBuf 版本和共享配置，并连接同一 PostgreSQL 与 Redis 实例。Redis 数据可以重建；PostgreSQL、附件对象和配置备份必须形成同一恢复点。

## 3. 对象存储

| Provider | 级别 | 必需配置 | 运行与备份边界 |
| --- | --- | --- | --- |
| Local filesystem | Supported，默认 | `STORAGE_DRIVER=local`、`STORAGE_LOCAL_PATH` | 适用于单机 Web/Worker；两个进程必须共享同一持久卷。目录与 PostgreSQL 一起备份和恢复，不属于可重建缓存 |
| AWS S3 | Optional | `STORAGE_DRIVER=s3`、Region、Bucket、Access Key、Secret Key；`S3_ENDPOINT` 留空 | Bucket 保持私有；Web 写入原件，Worker 读取原件并写入派生对象。Bucket 版本控制、跨区域复制或独立对象备份由部署者配置 |
| S3-compatible API | Optional | 与 AWS S3 相同，另按服务设置 HTTP(S) `S3_ENDPOINT` 和 `S3_FORCE_PATH_STYLE` | 只有通过应用 `HeadBucket`、上传、读取、派生、授权下载、回收和备份验收的实例进入发布记录；厂商名称本身不构成兼容证明 |

多 Web 实例必须使用经过验证的共享对象存储。公开 Bucket、每个实例各自保存本地附件、只备份数据库对象键或在未迁移对象前直接切换 storage driver 都不受支持。

## 4. SMTP 邮件

V1 使用标准 SMTP 发送验证、密码重置和通知邮件，不提供收件箱、IMAP、POP3 或域名邮箱托管能力。生产环境必须使用真实 SMTP；Mailpit 只用于开发、测试和 CI。

| 模式 | 级别 | 典型配置 | 验收要求 |
| --- | --- | --- | --- |
| Implicit TLS | Supported | `SMTP_PORT=465`、`SMTP_SECURE=true` | TLS 建连、认证、From、验证邮件、重置邮件和通知邮件真实送达 |
| STARTTLS | Supported | 通常 `SMTP_PORT=587`、`SMTP_SECURE=false` | Provider 必须声明该端口支持 STARTTLS；与 465 执行相同送达验收 |
| 无认证 SMTP | Supported when explicitly provided | `SMTP_USER` 与 `SMTP_PASSWORD` 同时留空 | 只适用于可信内网中继或测试服务；公网部署仍须验证中继限制和投递结果 |
| Mailpit `1025` | Development only | `SMTP_SECURE=false`，无认证 | 只证明应用协议、模板和错误状态，不构成真实邮件送达证据 |

`SMTP_USER` 与 `SMTP_PASSWORD` 必须同时设置。密码必须是 Provider 指定的 SMTP 凭据，而不是云控制台登录密码或通用 AccessKey。`SMTP_FROM` 必须由 Provider 允许发送；SPF、DKIM、DMARC、退信处理、发送配额和域名信誉属于部署者与邮件 Provider 的运行责任。

Worker 只自动重试能够证明 SMTP 尚未接受邮件的临时故障。认证或地址永久拒绝进入 `failed`；DATA 后断线、通用 Socket 超时、Worker 中断或 SMTP 成功后的本地完成失败进入 `outcome_unknown`，并要求管理员确认重复投递风险后重放。

## 5. OAuth

| Provider | 级别 | 配置与行为 |
| --- | --- | --- |
| GitHub OAuth | Optional | 同时设置 `GITHUB_CLIENT_ID` 与 `GITHUB_CLIENT_SECRET`；回调固定为 `${APP_URL}/api/auth/callback/github`。未配置时入口不显示；注册模式不是 `open` 时，既有绑定可以登录，新 OAuth 用户创建被拒绝 |
| 其他 OAuth/OIDC | Out of scope | Google、Linux.do 和通用 OIDC 尚未实现，不接受把任意端点填入 GitHub 变量的兼容方式 |

Better Auth 继续拥有 OAuth Account、Session、Cookie 与账号关联语义。Provider Secret 不进入 PostgreSQL 站点设置、浏览器响应、日志或审计导出。

## 6. 部署与网络边界

| 入口 | 级别 | 合同 |
| --- | --- | --- |
| Linux amd64/arm64 Docker Compose | Supported | 官方 GHCR 单镜像；Web、Worker、PostgreSQL、Redis 四个常驻服务 |
| 宝塔单文件 Compose | Supported | `compose.baota.yml`、四个固定容器名、无需 `.env`、稳定 `latest` 通道；同一 Docker 主机默认只运行一套。Release 工具通过 `backup --baota` 导出兼容标准恢复的归档，S3 媒体另需 Provider 快照/版本；隔离恢复使用 `--keep-stopped` 后再切换 Provider |
| Linux x64 standalone | Supported | Node.js 24、官方 tar.gz、systemd 或 PM2 模板；Web 固定回环监听 |
| 源码工作区 | Development only | Node.js 24、pnpm 11；不作为稳定支持产物身份 |

生产 Web 只绑定 loopback，并由 HTTPS 反向代理公开。官方提供 Nginx 示例；其他代理只有在保留 Host、协议、请求体上限并按 `AUTH_TRUSTED_PROXIES` 合同处理客户端 IP 时受支持。PostgreSQL 和 Redis 默认不发布公网端口。

## 7. 配置完整性

唯一配置字段说明在[配置参考](./12-configuration-reference.md)。以下组合必须由同一部署同时满足：

- `APP_URL` 是唯一规范公网 Origin，影响 Cookie、邮件链接和 GitHub OAuth 回调；额外 Origin 只通过 `AUTH_TRUSTED_ORIGINS` 明确加入。
- Web 与 Worker 使用相同 `AUTH_SECRET`、`TOPIC_VIEW_PREVIOUS_AUTH_SECRETS`、`MAIL_PAYLOAD_KEY`、SMTP、数据库、Redis 和存储配置。
- `SMTP_USER`/`SMTP_PASSWORD`、`GITHUB_CLIENT_ID`/`GITHUB_CLIENT_SECRET` 必须成对出现。
- S3 模式必须完整设置 Region、Bucket、Access Key 和 Secret Key；Endpoint 只接受 HTTP(S) 且不得包含用户信息、查询或 fragment。
- 生产示例占位密钥、HTTP 公网 `APP_URL`、缺失的 Provider 组合和镜像/迁移版本不一致必须在启动前失败。

## 8. 发布证据

自动化证据至少包括：环境 Schema 单元测试、真实 PostgreSQL/Redis/Mailpit 集成、local Provider 探针、Compose 策略检查、Web/Worker preflight、doctor、amd64/arm64 镜像冒烟和 Linux x64 归档启动。当前自动化存储探针只覆盖 `local`，不构成任何 AWS S3 或 S3-compatible 厂商、产品或具体实例的兼容证明。

S3 是已经实现的 Optional 协议合同。每个实际 AWS S3 或 S3-compatible 实例仍须人工完成并记录 `HeadBucket`、`PutObject`、`GetObject`、`DeleteObject`，以及派生对象、授权下载、对象回收和 Provider 级备份/恢复验收；只有该具体实例的全部结果通过后，才能把它写入本次部署的验收记录。

正式实例还必须记录：

1. `nextbuf doctor` 的脱敏结果；
2. 实际 PostgreSQL/Redis 主版本和部署入口；
3. SMTP TLS 模式、From 和三类邮件送达结果；
4. local 备份恢复，或具体 S3 实例的 `HeadBucket`、`PutObject`、`GetObject`、`DeleteObject`、原件/派生对象、授权下载、对象回收及 Provider 级备份/恢复结果；
5. GitHub OAuth 未启用时入口隐藏，启用时既有账号与注册模式边界；
6. HTTPS、可信代理、Web/Worker 版本和运行容器 Digest。

未经上述实例级验收的厂商只能记录为“按协议配置，待验证”，不能写成 NextBuf 官方认证 Provider。
