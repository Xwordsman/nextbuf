# `v0.13.9` 最终 Beta 发布说明

> **重要状态说明：** `v0.13.9` 标签流水线的双架构镜像冒烟和不可变 GHCR manifest 已完成，但 Linux x64 standalone 归档因 pnpm 依赖链接被展平而无法启动，GitHub Release 资产未完成。标签与已生成镜像保持不可变；`v0.13.9` 不是完整、受支持的发布，也不能设为升级基线。下面保留当时的历史说明和命令，不作为当前升级指引。替代版本 `v0.13.10` 已完整发布，其升级与交付证据见 [`v0.13.10` 发布说明](./18-v0.13.10-release-notes.md)。

`v0.13.9` 是进入 `v1.0.0` 稳定化之前的最后一个 Beta 加固版本。它不增加社区产品功能，不新增数据库迁移，不重写 UID、用户名、主题编号、回复楼层、角色、信任状态、通知或附件引用。

## 1. 主要变更

- 注册限流、身份审计和匿名浏览统一使用 Better Auth `1.6.23` 的客户端 IP 解析；可信代理只接受明确 IP/CIDR，并拒绝 `/0`、zone IPv6 和运行时不支持的映射 CIDR。
- 官方 Nginx 示例覆盖客户端传入的 `X-Forwarded-For`；非 Docker Web 包装器固定监听 `127.0.0.1`，公网连接必须经过同机反向代理。
- 匿名附件交付同时要求已发布 Post、公开/关闭 Topic 和 public Node；节点改为 hidden 后不再通过附件 URL 形成公开旁路。
- Prisma 升至 `7.9.1`，PostCSS 固定为 `8.5.24`；根项目和非 Docker runtime lockfile 分别执行生产依赖审计。
- 非 Docker 归档固化源码版本、完整 commit 和 commit 时间，原样保留 Next.js standalone 的 pnpm 运行依赖链接；systemd、PM2、CLI、Web 和 Worker 使用正确的 `runtime/` 工作目录及统一 dotenv 加载顺序。
- `nextbufctl` 使用内核文件锁串行化启动、停止、备份、恢复和升级；备份先停止 Web/Worker，验证 PostgreSQL dump，并保存附件列表及逐文件 SHA-256。
- 升级在备份和迁移前拉取目标镜像并核对镜像内部版本；目标 setup 开始后的失败保留目标版本、停止 Web/Worker 并输出日志，避免旧代码自动读取可能已经变化的状态。

## 2. 数据与迁移

`v0.13.9` 冻结的迁移清单与 `v0.13.8` 完全相同，共 13 条追加式 PostgreSQL 迁移。升级不会：

- 创建、删除或回填业务表数据；
- 改变现有用户 UID、Topic number 或回复 position；
- 清理草稿、会话、OAuth 账号、别名、角色、信任、治理、互动、通知、审计或 Outbox；
- 移动或重新编码现有头像和附件。

迁移集合相同不等于可以跳过升级演练。运行时版本门禁、镜像身份、备份和恢复脚本均有变化，正式发布仍必须通过精确 `v0.13.8 -> v0.13.9` 测试。

## 3. 支持的升级路径

受支持的直接来源是精确 `v0.13.8`。更早版本先按各版本发布说明顺序升级到 `v0.13.8`。升级前必须：

1. 确认 PostgreSQL、Redis、Web 和 Worker 当前健康。
2. 运行 `./nextbufctl doctor` 并保存结果。
3. 将最近一次有效备份复制到异机；S3 模式同时确认 Provider 版本控制或快照。
4. 记录当前镜像 Digest、`.env`、附件规模和最新迁移。

精确版本入口执行：

```bash
./nextbufctl upgrade 0.13.9
./nextbufctl status
./nextbufctl doctor
```

`upgrade` 会自动创建新的停写一致性备份。升级完成后抽查登录、管理员权限、主题/回复、草稿、附件、通知和 Worker，并记录 `/api/version` 返回的 version、commit 与 buildTime。

宝塔单文件 `latest` 入口仍通过面板拉取并重建四个常驻容器；正式变更前应在面板完成数据库和附件的实例级备份。需要可审计的精确版本、自动备份和失败停机语义时使用 `.env + compose.yml + nextbufctl` 入口。

## 4. 失败与恢复

- 目标镜像拉取或内部版本核对失败发生在备份/迁移前，当前 `NEXTBUF_VERSION` 保持 `0.13.8`，原服务继续运行。
- 备份失败时工具清理临时目录和 `.partial` 文件，并尽力恢复升级前正在运行的 Web/Worker。
- 目标 setup 一旦开始，后续失败会保留 `NEXTBUF_VERSION=0.13.9` 并停止 Web/Worker。修复可重试配置后再次运行目标 setup，或从升级前备份显式恢复。
- 不使用“只改回旧镜像标签”作为恢复方案。按 [ADR-0015](./adr/0015-production-packaging-setup-and-recovery.md) 恢复 PostgreSQL、附件、配置和匹配版本镜像。

## 5. 发布门槛

正式标签必须同时通过：

- 格式、Lint、严格类型、单元、真实 PostgreSQL/Redis/Mailpit 集成和 Playwright；
- amd64/arm64 原生镜像空安装、首次管理员与 Web/Worker 健康；
- amd64 空卷恢复、PostgreSQL/Redis/Worker/SMTP/存储故障注入；
- 目标镜像错标拒绝、setup 后故障停机、幂等重试和 `v0.13.8 -> v0.13.9` 数据保留升级；
- Linux x64 归档 checksum、systemd/PM2 路径、setup、Web、Worker、首次管理员、doctor 和 `/api/version` 身份；
- 不可变双架构 GHCR manifest、SBOM、provenance、SHA-256 和 GitHub Release。

## 6. 已知限制

- 在线成员跟踪仍是明确空状态。
- 14 天账号注销最终执行器尚未实现；已有注销请求可以撤销，但不会自动匿名化。
- OAuth-only 管理员缺少密码二次验证路径，正式运营至少保留一个 active 邮箱密码管理员。
- S3 备份依赖对象存储自身版本控制或快照，`nextbufctl` 不复制远端对象。
- 非 Docker 发布包只提供 Linux x64；Linux arm64 使用容器镜像。

这些限制属于 `v1.0.0` 稳定化范围或已记录的部署边界，不在 `v0.13.9` 中提前增加新功能。
